# 勤怠管理システム ロールバック手順書

## 1. 目的と適用範囲

リリース後に障害が発生した場合に、影響を抑え、アプリケーションまたはデータベースを安全に復旧する手順を定める。

> **重要:** 現行リポジトリはローカルデモ向けで、本番用のリリース基盤やバージョン管理された DB マイグレーションは定義されていない。本番環境でこの手順の DB 切替・復元をそのまま実施してはならない。本番は利用中の DB サービス固有の復旧手順と承認フローを別途定めること。

## 2. ロールバック判断

次のいずれかに該当する場合、変更の追加投入を停止し、リリース責任者へ連絡する。

- API のヘルスチェックが失敗する、または主要な画面・API が利用できない。
- 勤怠・休暇データの欠損、誤更新、重複が疑われる。
- 認証情報や個人情報の漏えいなど、セキュリティ上の問題が疑われる。
- 所定の監視時間内にエラー率や応答時間が許容値へ戻らない。

| 状況 | 対応 |
| --- | --- |
| アプリだけに問題があり、DB スキーマとデータに互換性がある | 直前の正常なフロントエンド・バックエンド成果物へ戻す |
| スキーマ変更が原因、または旧アプリとの互換性が不明 | 書き込みを止め、DB を変更せず責任者・DB 管理者へエスカレーションする |
| データ破損・誤更新が疑われる | 直ちに書き込みを止め、現状の保全コピーを取得してから復元可否を判断する |
| セキュリティ事故が疑われる | 公開経路を遮断し、証跡を保全する。単純な旧版戻しだけで終了しない |

## 3. 共通の初動

1. 障害を検知した時刻、症状、影響利用者、対象リリースのコミット ID を記録する。
2. 追加デプロイ、初期化 SQL の再実行、DB データ領域の削除を停止する。
3. 可能なら新規書き込みを止め、利用者へメンテナンス中であることを案内する。
4. DB を操作する前に、現在の状態を別ファイルへ保全する。保全ファイルには勤怠情報が含まれるため、アクセス権を制限する。
5. 影響が DB スキーマやデータに及ぶ可能性がある場合は、アプリだけを戻しても安全とは判断せず、DB 管理者の承認を得る。

## 4. アプリケーションのみを戻す

この手順は、直前の正常なフロントエンド・バックエンドの成果物が保管されており、現行 DB と互換であると確認できる場合に限る。

1. フロントエンドとバックエンドを停止する（実行中の各ターミナルで `Ctrl+C`）。DB は停止・削除しない。
2. デプロイ記録から直前の正常な成果物とコミット ID を特定する。成果物が特定できない場合は、ソースの最新版から代替ビルドせず作業を止める。
3. 運用環境で定めたリリース方式に従い、フロントエンドとバックエンドの両方を同じ正常リリースへ戻す。片方だけを戻す場合は API 互換性を確認する。
4. DB は変更せずにアプリを起動し、次の確認を行う。
   - `GET /actuator/health` が `UP` を返す。
   - 画面表示、勤怠・休暇の参照が成功する。書き込み確認は検証環境、または本番環境で事前承認されたテスト用従業員・日付に限定し、実在する従業員の勤怠レコードを検証目的で変更しない。
   - エラーログと監視値が正常に戻る。
5. 利用再開を周知し、原因・対象リリース・実施者・確認結果を記録する。

このリポジトリには本番成果物を配置・切替するスクリプトがないため、実運用ではこの節の「運用環境で定めたリリース方式」を先に具体化すること。

## 5. ローカル Compose 環境の DB 保全

### 5.1 変更前バックアップ

リポジトリの `backend` ディレクトリで実行する。実行前に DB が起動していることを確認する。

```bash
set -euo pipefail
mkdir -p ../backups
chmod 700 ../backups
backup_file="../backups/attendance_db_$(date +%Y%m%d_%H%M%S).dump"
docker compose exec -T postgres pg_dump -U attendance_user -d attendance_db -Fc > "$backup_file"
test -s "$backup_file"
docker compose exec -T postgres pg_restore --list < "$backup_file" > "${backup_file}.toc"
test -s "${backup_file}.toc"
```

ファイルが空、または `pg_restore --list` が失敗した場合はデプロイを進めない。バックアップはリポジトリへコミットせず、アクセス制限された保管先へ移す。

### 5.2 バックアップからの隔離復元テスト

元の `attendance_db` を上書きせず、別名のデータベースへ復元して内容を確認する。`backup_file` は実際に作成したバックアップファイルのパスに置き換える。

```bash
set -euo pipefail
backup_file="../backups/attendance_db_YYYYMMDD_HHMMSS.dump"
docker compose exec -T postgres createdb -U attendance_user attendance_restore
docker compose exec -T postgres pg_restore -U attendance_user -d attendance_restore < "$backup_file"
```

復元した DB を使ってアプリを一時起動する場合は、`backend` ディレクトリで次を実行する。

```bash
SPRING_DOCKER_COMPOSE_ENABLED=false SPRING_DATASOURCE_URL=jdbc:postgresql://localhost:5432/attendance_restore mvn spring-boot:run
```

画面・API・対象データを確認したらアプリを停止する。`attendance_restore` は検証用コピーであり、確認後も元 DB の代わりに自動切替しない。

### 5.3 DB の切戻し・復元

現行構成ではスキーマ変更の履歴管理や安全な DB 切替手段がない。元 DB の上書き復元は、バックアップ取得後の勤怠データを失うおそれがあるため、一般利用者がこの文書だけで実施してはならない。

データ破損時は、書き込み停止後に現在の DB も別の保全先へ退避し、復旧時点と失われる更新を責任者・DB 管理者が承認する。承認後、DB 管理者が対象環境専用の復元・切替手順を実施し、隔離復元で検証してから利用を再開する。本番 DB はサービス提供元の Point-in-Time Recovery（指定時点復旧）等を優先し、利用中サービスの正式な復旧手順に従う。

## 6. 禁止事項

- `docker compose down -v`、Docker volume の削除、DB ディレクトリの削除をロールバック手段として使わない。
- バックアップを検証せずに既存 DB へ復元しない。
- スキーマ変更の互換性が確認できない状態で、旧アプリを DB に接続しない。
- 初期化 SQL を既存データの復元やマイグレーションの代用として使わない。
- 障害原因・影響範囲を記録せず、復旧完了として扱わない。

## 7. 復旧完了記録

復旧日時、障害内容、影響範囲、戻したアプリのコミット ID、DB 操作と復元時点、承認者、検証結果、残課題を記録する。再発防止の変更は通常のレビューとテストを経て別リリースにする。
