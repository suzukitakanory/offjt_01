# 勤怠管理システム導入手順書

## 1. 目的と適用範囲

この手順書は、勤怠管理システムを開発・研修用のローカル環境へ導入し、起動確認する手順を定める。導入担当者以外でも、この文書とリポジトリだけで作業を完了できることを前提とする。

> **本番利用禁止:** 現行実装はデモ用途であり、認証・従業員間のアクセス制御がない。DB接続情報も開発用の固定値で、Hibernateの自動スキーマ更新が有効になっている。本番環境や複数利用者がアクセスするネットワークへ公開してはならない。実運用への導入は、認証、秘密情報管理、本番向け設定、DBマイグレーション方式、監視・バックアップを整備してから別途設計する。

本システムは React + Vite のフロントエンド、Spring Boot の API、PostgreSQL の構成である。フロントエンドは `/api` を同一オリジンの API へ転送するため、ローカル手順では Vite 開発サーバーを使う。

## 2. 前提環境

本手順は Windows 上の WSL2 Ubuntu で実行する。手順を始める前に、[開発ガイド](../../CONTRIBUTING.md)の「WSL2 環境のセットアップ」と「必須ツール」「ツールのインストール」を完了し、Ubuntu のターミナルを開く。Windows の PowerShell ではなく、WSL2 内で以降のコマンドを実行する。

## 3. 作業前確認

### 必要なソフトウェア

- Git 2.30 以上
- Java 21
- Maven 3.8 以上
- Node.js 18 以上、pnpm 9 以上（フロントエンドの lockfile v9 に対応するバージョン）
- Docker と Docker Compose v2
- ブラウザー（Chrome、Firefox、Safari、Edge のいずれか）

導入先で各コマンドが実行できることを確認する。

```bash
git --version
java -version
mvn -version
node --version
pnpm --version
docker compose version
```

### 作業上の注意

- データベースの初期化 SQL は、PostgreSQL のデータ領域が初めて作られるときだけ自動実行される。既存データのある環境で、初期化のためにデータ領域を削除してはならない。
- `attendance_user` と `attendance_password` は開発専用の固定認証情報である。実運用の認証情報として使用しない。
- 勤怠データは個人情報として扱い、バックアップファイルのアクセスを制限する。

## 4. 導入手順

以下の取得例はこの教材リポジトリのURLを使用する。フォークを利用する場合はURLを置き換える。clone後、アプリケーションのルート `attendance-system-workshop-ja-v1.1.1/` に移動して以降のコマンドを実行する。

### 4.1 ソース取得と品質確認

```bash
git clone https://github.com/suzukitakanory/offjt_01.git offjt_01
cd offjt_01/attendance-system-workshop-ja-v1.1.1
git status --short
```

リリース対象として承認されたブランチまたはコミットを使う。作業ツリーに未コミット変更がある場合は、導入作業を始めず、変更の所有者と扱いを確認する。

バックエンドとフロントエンドの依存関係を解決し、テスト・静的検査・ビルドを実行する。

```bash
cd backend
mvn clean verify
cd ../frontend
pnpm install --frozen-lockfile
pnpm lint
pnpm build
cd ..
```

いずれかが失敗した場合は導入を中止し、原因を解消してから再実行する。テスト結果を確認せずに失敗を無視して先へ進まない。

### 4.2 PostgreSQL の起動

```bash
cd backend
docker compose up -d
docker compose ps
```

`postgres` が `healthy` になるまで待つ。状態が `unhealthy` または `exited` の場合はログを確認し、解消するまでアプリケーションを起動しない。

```bash
docker compose logs --tail=100 postgres
```

この構成は開発用で、DB ポート 5432 をホストへ公開する。信頼できないネットワークに接続した端末では起動しない。

### 4.3 バックエンドの起動

バックエンド用ターミナルで、`backend` ディレクトリから実行する。

```bash
mvn spring-boot:run
```

起動ログにエラーがなく、別ターミナルからヘルスチェックが成功することを確認する。

```bash
curl -fsS http://localhost:8080/actuator/health
```

### 4.4 フロントエンドの起動

別ターミナルでリポジトリルートから実行する。

```bash
cd frontend
pnpm dev
```

ブラウザーで `http://localhost:5173` を開き、画面が表示されることを確認する。勤怠・休暇の登録と再読み込み後の表示を確認し、API 通信エラーがないことを確認する。

### 4.5 導入完了判定

- Maven の検証とフロントエンドの lint・build が成功している。
- PostgreSQL が healthy で、API の `/actuator/health` が `UP` を返す。
- ブラウザーから画面を開け、勤怠・休暇の読み書きができる。
- 使用したコミット ID、実行結果、導入日時、担当者を記録した。

導入時の設定や実行結果に不明点があれば、完了扱いにせず記録して確認する。

## 5. 停止

フロントエンドとバックエンドそれぞれのターミナルで `Ctrl+C` を押す。Compose の DB を停止するときは `backend` ディレクトリで実行する。

```bash
docker compose stop
```

`docker compose down -v` は PostgreSQL の永続データを削除するため実行しない。

## 6. 実運用導入に必要な追加設計

このリポジトリには本番用の配信設定やリリース自動化が含まれていない。実運用を開始する前に、少なくとも以下を決定・実装する。

- 認証、認可、従業員ごとのアクセス制御と HTTPS
- 環境変数または秘密情報管理サービスによる認証情報の注入
- Hibernate の `ddl-auto: update` を無効にし、レビュー可能なバージョン管理付き DB マイグレーションを導入
- 本番向け Actuator の公開範囲とヘルス情報の制限
- フロントエンドの静的配信、API の配置、ネットワーク境界、冗長化
- DB のバックアップ保持期間、復旧目標、復元試験、担当者と承認手順
- デプロイ対象の不変な成果物、リリース記録、監視とロールバック判定基準
