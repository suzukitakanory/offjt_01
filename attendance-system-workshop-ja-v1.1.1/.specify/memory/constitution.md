
# 勤怠管理システム チーム憲章

## 基本原則

### １. 責任の所在
- 変更をマージした人が、その変更の最終責任を負う。
- 開発者は、マージするすべてのコード変更を説明できなければならない。説明できないコードをマージしてはならない。
- AIが生成した出力も開発者の成果物とみなし、担当する開発者がレビューして理解する。
- コードの作成方法にかかわらず、責任者を明確にする。

### ２. 進め方の選択
- 本PBLは仕様駆動開発で実施する。
- 実装に着手する前に、仕様と受入条件を更新または確認する。
- 試作ではバイブコーディングを利用してもよい。
- 本番に入れるコードは仕様、レビュー、テスト、マージの要件を満たさなければならない。
- 試作の速さと本番コードの品質管理を両立させる。

### ３. タスクの粒度
- タスクは単独でテストできる単位に分割する。
- 原則として、１つのPRで実装する機能は１つとする。
- PRの変更行数は４００行以内、変更ファイル数は８ファイル以内とする。
- いずれかの上限を超える作業は、複数のPRに分割する。
- 小さな変更単位にし、個別のテストとレビューを可能にする。

### ４. 並列実行
- １タスクにつき、作業ブランチは１つ、担当者は１人とする。
- 同時進行できるタスクは２件までとする。
- 同時に稼働できるクラウドエージェントは最大２件とする。
- 同一タスクを複数のブランチや担当者に分けてはならない。
- 作業の競合を抑え、責任者を明確にする。

### ５. セッションの前後
作業セッションの開始前に、担当者は次の項目を確認しなければならない。
- `git status` を確認する。
- 最新の変更を取得する。
- 作業ブランチを確認する。
- 当日の作業範囲を確認する。
- 受入条件を確認する。

作業セッションの終了後に、担当者は次の項目を実施しなければならない。
- 差分を確認する。
- テストを実行する。
- Lintを実行する。
- 意図しない変更がないことを確認する。
- 人がテスト結果を確認する。

- 開始時と終了時の確認を定着させ、作業の前提と成果を明確にする。

### ６. レビュー
- すべてのPRは実装担当者以外がレビューする。
- レビューなしのマージと、実装者自身によるレビュー承認を禁止する。
- AIレビューの後に人によるレビューを行う。AIレビューで人によるレビューを代替してはならない。

- レビュー担当者は次の順序で確認する。
1. 変更ファイル一覧
2. 削除行
3. テスト
4. 実装
5. 依存追加
6. ソース理解確認

### ７. 禁止事項
次の行為を禁止する。
- 本番データベースへ接続すること。
- 機密情報をAIに入力すること。
- テストを無効化すること。
- 確認を省略する起動オプションを使用すること。

### ８. 止める基準
- 同一の修正に３回失敗した場合、作業を止めて人に引き継ぐ。
- 担当者が理解できないコードや差分は破棄する。
- レビュー担当者が適切にレビューできないと判断した場合も、PRをマージせず作業を停止する。
- 原因を把握し、理解できる範囲とレビュー可能な状態を回復してから再開する。

### ９. 記録
- 仕様は実装に先立って更新し、受入条件とともに記録する。
- 各PRにはAIの利用内容を記載する。
- レビュー担当者が作成経緯と検証状況を確認できるようにする。
- 記録により、実装が意図した仕様に沿うこととAI利用の範囲を追跡できるようにする。

## ガバナンス

- この憲章は、仕様、実装、テスト、PRレビューを含むプロジェクト作業に適用する。
- すべてのPRはマージ前に本憲章への準拠を確認する。
- 個別の例外を認めない。規則の変更が必要な場合は、改正手続きに従って憲章を改正する。

- 改正は文書化した変更として提案し、チームのレビューと承認を経てから適用する。
- 改正によって必須の作業手順が変わる場合、影響を受ける仕様とワークフローの説明を更新する。

- 本憲章にはセマンティックバージョニングを適用する。
- 原則またはガバナンス規則の削除、もしくは互換性のない再定義にはMAJORを適用する。
- 新しい原則やセクションの追加、または要件の実質的な拡張にはMINORを適用する。
- 方針を変更しない文言の修正や明確化にはPATCHを適用する。
