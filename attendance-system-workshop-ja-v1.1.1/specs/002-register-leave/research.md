# Research: 休暇登録

## 既存の日次勤怠レコードを再利用する

- **Decision**: 休暇は新しいテーブルを作らず、既存の `attendance_records` に保存する。休暇区分は `status`、メモは `notes` に置く。
- **Rationale**: テーブル定義と `AttendanceRecord` はすでに REQ-UC004 を関連要件とし、従業員と日付の一意制約が「1日1件」と一致する。勤務時間と同じ日次記録に揃えると、同日の勤務と休暇が二重に存在しない。
- **Alternatives considered**: 休暇専用テーブルは日付の重複を別制約で守る必要があり、勤務時間との競合を増やす。採用しない。

## 保存値は既存コード、画面と API は要件の表示名

- **Decision**: 永続化は `SICK_LEAVE`、`PERSONAL_LEAVE`、`BUSINESS_TRIP` を使う。API と画面の選択肢は `Sick Leave`、`Personal Leave`、`Business Trip` とし、境界で変換する。
- **Rationale**: テーブル定義書がこの3コードを休暇登録のステータスとして既に定め、`VARCHAR(20)` に収まる。仕様が利用者に提示する名称は英語の表示名である。表示名をそのまま保存すると設計書とずれる。
- **Alternatives considered**: 表示名を `status` に直接保存する案は、既存の設計書と勤務ステータス `WORK` のコード体系から外れる。採用しない。

## 休暇操作は勤怠の一括保存 API から分ける

- **Decision**: 休暇の作成、日付取得、期間取得、更新、削除は `/api/leaves` で行う。既存の `POST /api/attendance` は使わない。
- **Rationale**: 既存の勤怠 API は未実装の登録・更新兼用で、呼び出し側が従業員 ID を指定する。仕様は新規保存と既存変更を分け、存在しない対象を成功扱いせず、他者の休暇を扱えないようにする。専用 API にすると作成の409と更新の404を混ぜずに検証できる。
- **Alternatives considered**: 既存の勤怠 POST に休暇区分を足す案は、作成と更新の区別と本人限定を同じ入口で崩す。採用しない。

## デモ従業員 ID はサーバー設定だけが決める

- **Decision**: 対象従業員はサーバー設定のデモ従業員 ID（既定 `EMP001`）だけとする。要求や URL で従業員 ID を受け取らない。認証は追加しない。
- **Rationale**: 仕様は従業員本人の記録だけを扱う。認証をこの機能に足すと、承認フローと同じく対象外の範囲に入る。ID を呼び出し側に選ばせると、他の従業員の記録を指定できる。設定値に固定すれば、デモの範囲で FR-014 を満たせる。
- **Alternatives considered**: パスに従業員 ID を残す現行の勤怠 API 形は、本人確認なしでは他者の記録を操作できる。認証付きの複数従業員対応は本仕様の対象外。どちらも採用しない。

## 勤務日は確認後に同じ行を休暇へ変える

- **Decision**: 行がない日は休暇行を作成する。休暇行がある日の追加作成は409 `ERR02003` とし、変更または削除へ誘導する。勤務行がある日は、`confirmReplaceWork` がない作成を409 `ERR02005` とし、時刻を変えない。従業員が時刻の削除を確認した再送だけ、同じ行の状態を休暇にし、出勤・退勤時刻を空にする。取得・更新・削除は休暇コードの行だけを休暇として扱う。
- **Rationale**: REQ-UC004 は任意の日付へ休暇を登録できることを求めている。1日1行の一意制約は、2行を作らず既存行を変えることで守れる。確認なしの上書きは勤務時間を黙って消すため、採用しない。
- **Alternatives considered**: 勤務日を常に409で拒否する案は、誤って勤務を入れた日を休暇に直せない。黙って勤務行を休暇へ書き換える案は、時刻の消失を従業員が選べない。どちらも採用しない。

## 公式のローレベル設計はワークショップの設計書に置く

- **Decision**: シーケンス、画面、テーブル、API、メッセージ、開発状態の正本は `offjt_01/attendance-system-workshop-ja-v1.1.1/docs/` に置く。`specs/002-register-leave/` の data-model と契約は、その正本への仕様キット側の写しとする。
- **Rationale**: ワークショップのローレベル設計手順が、成果物のパスと更新順を定めている。仕様キットの計画だけでは実装者が参照する設計書が更新されない。
- **Alternatives considered**: 仕様ディレクトリだけに設計を残す案は、画面設計書・OpenAPI・開発状態が古いままになる。採用しない。

## エラー区分はメッセージ ID に揃える

- **Decision**: 休暇 API の `error` は `ERR02002`、`ERR02003`、`ERR02005`、`ERR03004` から `ERR03008` を使う。成功文言は `SUCCESS02002` から `SUCCESS02004` とし、画面が表示する。
- **Rationale**: REQ-UC003 の API がメッセージ ID を `error` に入れている。休暇だけ別の記号にすると、画面とメッセージ定義書が二重管理になる。
- **Alternatives considered**: `INVALID_INPUT` などの意味コードは安定するが、既存のメッセージ定義書と画面設計の ID 体系から外れる。採用しない。

## 検証は既存のテスト手段だけを使う

- **Decision**: バックエンドは JUnit 5、MockMvc、Testcontainers の PostgreSQL を使う。フロントエンドは TypeScript ビルドと ESLint を使う。画面の受け入れは既存の Cucumber と Playwright に `@REQ-UC004` を追加する。新しいライブラリは追加しない。テストを無効化する起動オプションは使わない。
- **Rationale**: 必要な検証手段は `pom.xml` と `e2e/package.json` に既にある。本番データベースには接続しない。
- **Alternatives considered**: フロント専用のテストランナー追加や、テストを飛ばす Maven オプションは、憲章の依存追加禁止とテスト無効化禁止に反する。採用しない。
